Dulu, waktu awal-awal bikin form untuk registrasi *user*, aku punya pikiran yang lumayan naif.

Pikirku: *"Ah, kan di Backend udah ada validasi. Kalau emailnya salah format atau *password*-nya kependekan, nanti Backend juga bakal nolak dan ngirim error 400. Yaudah, Frontend tinggal lempar aja datanya apa adanya."*

Logis, kan? Biar ngga kerja dua kali.

Tapi ternyata, setelah aplikasinya dipakai banyak orang... hancur lebur wkwkwk.

Setiap kali *user* salah ketik email, mereka harus nunggu loading sekian detik. Server ngerespon lambat. *User* bingung karena errornya muncul telat. Belum lagi kalau *user* iseng mencet tombol "Submit" berkali-kali saking gregetannya. 

Dari situ aku sadar satu hal:
> Frontend tidak boleh hanya menjadi tukang pos yang pasrah. Frontend harus jadi resepsionis yang cerewet.

### Resepsionis (FE) dan Brankas Utama (BE)

Bayangkan sebuah bank.

Backend adalah brankas utama dan manajer bank di ruang belakang. Mereka punya aturan super ketat (Pydantic, kalau di FastAPI). Tidak boleh ada data sampah yang masuk ke database.

Sedangkan Frontend adalah resepsionis yang duduk di lobi depan.

Kalau resepsionisnya malas, setiap ada nasabah yang bawa formulir kosong, dia akan langsung menyuruh nasabah itu jalan jauh ke ruang manajer. 

Lalu apa yang terjadi? Manajernya marah, nasabahnya disuruh balik lagi ke depan. Waktu terbuang. Antrean panjang. Server kelelahan memproses *request* yang sebenarnya dari awal udah jelas-jelas salah.

Resepsionis yang baik (Frontend yang solid) akan mencegat nasabah itu sejak awal:
> Maaf Pak, kolom emailnya belum pakai tanda '@'. Tolong diperbaiki dulu ya di sini, baru nanti saya antarkan ke manajer.

Cepat. Ngga perlu bolak-balik. Server lega, *user* juga ngga emosi.

### Zod: Kembaran Pydantic di Dunia Frontend

Sebagai anak Backend, kamu pasti cinta banget sama Pydantic (di Python/FastAPI) atau DTO untuk validasi data.

Nah, biar si "resepsionis" di Frontend ini pintar, kita membekalinya dengan sebuah *library* yang konsepnya persis 100% seperti Pydantic. Namanya **Zod**.

Kalau di Backend kamu nulis begini:
```python
# Backend - Pydantic
class UserCreate(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8)

```

Di Frontend, kita menulis "buku panduan" yang sama persis:

```typescript
// Frontend - Zod
import { z } from 'zod';

const formSchema = z.object({
  email: z.string().email({ message: "Format email salah bro!" }),
  password: z.string().min(8, { message: "Password minimal 8 karakter dong." })
});

```

Dengan Zod, kalau *user* ngetik *"budi_tanpa_gmail"*, tombol submit bahkan tidak akan menyentuh fungsi `fetch()` ke Backend. Zod akan langsung memblokirnya secara instan di layar HP *user* dan memunculkan tulisan warna merah: *"Format email salah bro!"*

Nggak ada *request* internet yang terbuang percuma. Indah banget.

### Mencegah Bencana "Double Submit"

Ada satu penyakit akut pengguna internet: kalau aplikasinya kerasa lambat dikit aja, jari mereka gatal pengen mencet tombol "Simpan" dua, tiga, sampai sepuluh kali.

Kalau Frontend ngga menangani ini, Backend bakal nerima 10 *request* yang sama persis dalam waktu 1 detik. Hasilnya? Database-mu bisa jebol atau data yang tersimpan jadi dobel-dobel.

Makanya, saat mengintegrasikan form, Frontend punya seni mengelola tombol:

```tsx
function FormRegistrasi() {
  // Kita bikin State penanda aktivitas
  const [isLoading, setIsLoading] = useState(false);

  const handleSubmit = async (data) => {
    // 1. Kunci pintunya!
    setIsLoading(true); 
    
    try {
      // 2. Kirim kurir ke Backend
      await fetch('/api/register', { ... }); 
    } finally {
      // 3. Apapun yang terjadi (sukses/gagal), buka lagi pintunya
      setIsLoading(false); 
    }
  };

  return (
    <button 
      disabled={isLoading} // Tombol mati total saat lagi loading
      className={isLoading ? 'warna-abu-abu' : 'warna-biru'}
    >
      {isLoading ? 'Lagi Muter...' : 'Simpan Sekarang'}
    </button>
  );
}

```

Hanya dengan tambahan atribut `disabled={isLoading}`, Frontend berhasil menyelamatkan Backend dari ribuan *spam request* tidak sengaja.

### Menerima Kenyataan: Error 400 dari Backend

Oke, Frontend udah melakukan validasi panjang lebar. Formnya udah sempurna. Emailnya valid, *password*-nya panjang. Resepsionis mengizinkan nasabah masuk ke ruang manajer.

Tapi, manajer (Backend) tetap menolak dengan error 400. Kenapa?
Karena ternyata email tersebut *sudah pernah didaftarkan* sebelumnya.

Hal seperti ini (ngecek ke *database*) adalah ranah absolut Backend. Frontend ngga mungkin tahu. Jadi, ketika ini terjadi, Frontend harus legowo menerima tamparan dari Backend, menangkap pesan errornya, dan memetakannya kembali ke layar.

```tsx
// Menangkap respon penolakan Backend
if (!response.ok) {
  const errorBackend = await response.json();
  
  // Kalau backend bilang emailnya udah ada
  if (errorBackend.detail === "EMAIL_ALREADY_EXISTS") {
    // Tampilkan notifikasi warna merah di bawah input email
    setError("email", { message: "Yah, email ini udah dipakai orang lain." });
  }
}

```

### Sebuah Orkestra yang Saling Melengkapi

Dan semakin dipikir-pikir...

Hubungan Frontend dan Backend saat mengirim data ini lebih dari sekadar melempar JSON. Ini adalah kolaborasi saling menjaga.

Frontend menjaga pintu depan agar Backend tidak kelelahan melayani hal-hal sepele.
Backend menjaga brankas belakang untuk memastikan tidak ada celah keamanan yang terlewat.

Masing-masing tidak ada yang lebih superior. Keduanya bekerja berdampingan.

Dan mungkin, ketika Frontend dan Backend bisa menyamakan frekuensi soal validasi dan bentuk data seperti ini... proses *development* tidak lagi terasa seperti medan perang antar divisi wkwkwk.

Semuanya jadi terasa masuk akal, aman, dan menenangkan.
